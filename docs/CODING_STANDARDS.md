# Стандарты работы над ИЗОБАРОЙ

<a id="scope"></a>

## Границы изменений

Развивать существующую одиночную 3D action-RPG локальными изменениями. Сохранять 3D-мир, текущий локальный движок, художественное оформление, подключённые изображения, совместимость сохранений и автономный запуск. Программные 3D-модели являются действующим оформлением игры.

Общая просьба «работать по roadmap/README» разрешает выполнение выбранного пакета в существующей игре. Смена движка, переписывание игры с нуля, переход к 2D, удаление ассетов или замена существующей графики примитивами, заглушками либо CSS-рисунками допустимы только по отдельному явному поручению владельца.

## Контекст задачи

<a id="code-context"></a>

### Код, игровое поведение и сборка

Перед изменениями прочитать [README](../README.md) и [архитектуру](ARCHITECTURE.md). Расположение и ответственность модулей описаны в архитектуре; команды разработки и проверок — в README и `package.json`.

При выполнении пакета [roadmap](../roadmap.md) прочитать вводную часть, выбранный пакет, его зависимости и критерии приёмки. Формулировки пакетов сохраняют исходные критерии: сверить выбранный пакет с таблицей статуса и его реализацией, чтобы не повторить уже выполненную работу.

<a id="docs-context"></a>

### Только документация

Прочитать изменяемые документы и источники исправляемых утверждений. Архитектуру и конкретный пакет roadmap читать, когда правка затрагивает их положения; обычная правка документации не требует выбора игрового пакета.

<a id="assets"></a>

## Ассеты и архив

[ASSETS.md](../ASSETS.md) описывает текущий каталог. [docs/asset-production/](asset-production/), [evidence/asset-audit/](../evidence/asset-audit/) и результаты в [output/assets/](../output/assets/) — архив завершённого производства и свидетельства происхождения, а не очередь работ. Исторические замечания не являются дефектами текущих файлов.

<a id="verification"></a>

## Проверки

- Для изменений кода выполнять подходящие проверки из [README](../README.md); если выбран пакет roadmap, также выполнять его проверки и критерии приёмки.
- Для правок только документации проверять ссылки, согласованность и diff; пересборка игры не требуется.

Указывать фактически выполненные проверки и ограничения.
